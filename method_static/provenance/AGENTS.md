# AGENTS.md

# VRILE Codex Instructions

Read and follow this file before modifying the repository.

## 1. Core rule

Make only the changes required by the current task.

Do not perform unrelated refactoring, cleanup, renaming, formatting, architecture changes, or speculative improvements. Prefer the smallest safe patch.

## 2. Scientific definitions

Preserve the confirmed definitions and the original `seaice_VRILEs` logic.

The event classes are exactly:

- `broad`
- `severe`
- `major_severe`

Do not replace `major_severe` with `major` and do not invent new event classes.

Do not silently change:

- event thresholds
- event windows
- background definitions
- lead-lag definitions
- regional definitions
- severity logic

If code, toolbox, paper, or task instructions conflict, report the conflict before changing scientific logic.

## 3. Statistical units and repeated observations

Define the independent statistical unit before inference.

For event-based diagnostics, repeated lag rows, grid cells, edge cells, or buffer rows are not independent events.

Use:

- Stage 6/7/8 local-event statistics: `event_id`
- Stage 9/10 major-cluster statistics: cluster `event_id`

Aggregate repeated observations within each unit first; then perform group inference on unit-level values or differences.

Never use row count, lag count, grid-cell count, or observation count as independent sample size.

Do not pool different `buffer_km` values into one event-level mean unless the current task explicitly defines a cross-scale aggregate.

### Stage 7

For each:

`region × variable × lag_group × event_id`

calculate:

- `event_mean`
- `background_mean`
- `difference = event_mean - background_mean`

An `event_id` enters statistics only when both sides are valid. Each event contributes one unit. Bootstrap confidence intervals must resample event-level `difference`.

Do not revert to row-level pseudoreplication.

## 4. Multiple testing and decision gates

When multiple tests are used to make a region-level status, score, or pass/fail decision:

1. define the correction family explicitly;
2. calculate raw p-values;
3. apply the configured FDR correction;
4. only then generate final boolean gates such as `significant`, `control_passed`, `supported`, or evidence scores.

Do not use patterns such as:

`any(raw_p < 0.05)`

across multiple variables, regions, radii, lag groups, or controls.

Keep raw and corrected p-values in separate columns.

A final evidence gate must use the corrected value when FDR is required.

## 5. Buffer-scale handling

The confirmed diagnostic radii are:

- `100 km`
- `300 km`
- `500 km`

Preserve all three unless the user explicitly changes them.

Treat radius as a scale/sensitivity dimension, not an independent event or independent evidence dimension.

Rules:

- retain `buffer_km` through event-level tables, controls, and robustness outputs;
- compare wrong regions at the same variable and same `buffer_km`;
- do not average 100/300/500 km together before inference;
- do not count the same variable at three significant radii as three independent evidence variables;
- evidence scoring may count unique supported variables;
- supported radii may be reported descriptively for scale-dependence or multiscale robustness.

## 6. Evidence aggregation

Do not score the same statistical contrast twice under different labels.

A robustness test of the same event-minus-background contrast is not automatically an independent evidence dimension.

Specifically:

- event-unit sign-flip is a robustness/randomization test, not a temporal placebo;
- sign-flip robustness must not independently increase `control_score`;
- wrong-region controls may affect `control_score` only after their required multiplicity correction and final gate;
- year-block bootstrap is confirmation of an already supported primary signal, not a search for a new significant variable;
- when confirming a buffer signal, match the same `variable` and `buffer_km`;
- supplementary cyclone or edge-wind evidence must not enter `mean_score` unless explicitly requested.

Keep `unavailable`, `insufficient_samples`, `not_supported`, and `supported` semantically distinct. Never convert missing or insufficient data into mechanism absence.

Active production code, scripts, output directories/files, CSV columns, reports, and figure titles must use version-neutral names. Do not introduce version labels into active production names.

## 7. Data lineage and validation provenance

Do not mix statistical outputs from different code versions or validation runs and present them as one current result.

For validation packages:

- use one validation root per run;
- record the current code hash when practical;
- mark reused unchanged inputs as `baseline_input`;
- mark files generated by the current run as `generated` or an equivalent explicit label;
- never copy an old statistical output and label it as newly validated;
- the manifest must identify the source or generating stage of key statistical outputs.

Do not claim runtime validation for evidence/report unless the corresponding files were actually generated with the current code and current validation inputs.

## 8. Plotting

All final figures must be generated with GMT.

Python may be used for:

- data reading
- preprocessing
- numerical computation
- statistics
- generation of GMT input tables

Do not add matplotlib, Cartopy, or other Python final-figure paths for convenience.

## 9. Regions and masks

Use the regional boundaries and mask semantics already confirmed by this project.

Do not redefine Arctic regions from general geographic intuition.

Do not infer mask codes from unrelated conventions.

For unknown codes, ambiguous boundaries, CRS metadata conflicts, or grid mismatches, inspect documentation and actual metadata first. Report unresolved ambiguity instead of guessing.

Do not silently regrid, remap, or reinterpret a mask.

## 10. Compatibility

Preserve compatibility with the current verified workflow.

Unless explicitly requested, do not change:

- file names
- directory structure
- output directories
- stage numbers
- CLI arguments
- existing CSV column names
- existing batch-script interfaces

When new audit fields are required, prefer adding columns or new summary files rather than renaming/removing existing fields.

Do not add silent fallback logic that changes scientific meaning.

## 11. Modification workflow

Before editing:

1. locate the current implementation;
2. identify the exact current logic;
3. check whether the requested behavior already exists;
4. determine the minimum required patch.

After editing:

1. run syntax/static checks;
2. run the smallest targeted validation;
3. inspect statistical units, key gates, and output fields;
4. verify the changed logic with actual outputs;
5. do not claim success without validation evidence.

Do not use a full pipeline rerun as a substitute for targeted validation unless explicitly requested.

## 12. Reporting

Report concisely:

- modified files/functions
- logic changed
- validation run
- actual result
- unresolved issue, if any

Do not provide unrelated observations or speculative improvements.

## 13. Priority of evidence

When instructions conflict, use:

1. user's latest explicit instruction
2. this `AGENTS.md`
3. current verified implementation
4. original `seaice_VRILEs` toolbox
5. paper or methodological documentation
6. model inference

Do not create a new scientific definition from inference alone.
